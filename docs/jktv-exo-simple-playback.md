# JKTV 1.7 Exo 简化与切站修正

## 决策依据（2026-11-22）

- 电视 1.6 日志 `webhtv-debug-log.txt`：两次播放同一约 14.36 Mbps、3840×2160 HEVC 渐进式资源，第二次经无法观察上游的外部本机回环代理，测得约 12.29 Mbps；21:37:00.962 缓冲归零，21:37:20.117 才恢复，累计 19.2 秒。第一轮也有约 5.1 秒重缓冲。解码器成功启动，不能把这次等待断言为解码失败；下载速率低于媒体码率，播放器设置本身不能提供缺少的数据。
- 用户提供的 OK影视 5.1.6 APK 的本地 JADX 输出 `C3/e.java:545-600`：Exo 构建使用固定时长的 LoadControl（默认缓冲级别为 1，对应 50 秒；启动阈值约 1 秒、重缓冲阈值 2 秒），没有 JKTV 当前按会话反复调节阈值的 `AutoLoadControl`。这是实物对照，不复用反编译代码。
- JKTV `ExoUtil.buildEnhancedLoadControl` 的自动配置使用 `AutoTargetLoadControl` 和 `AutoLoadControl`；日志中第二次会话启动阈值 3 秒、重缓冲阈值 15 秒。`ExoPerformanceSetting` 自动模式默认开启网络保护，第一轮速度变为 0.959。`Server.start` 从 9978 扫到 9998，日志地址会随端口变化。`HomeActivity.getVideo` 在普通站点新内容返回前隐藏网页并清空推荐行，导致底层空白可见。
- [Media3 官方 LoadControl 文档](https://developer.android.com/reference/androidx/media3/exoplayer/DefaultLoadControl.Builder)：固定的 `setBufferDurationsMs` 分别规定缓冲目标、启动和重缓冲阈值。固定策略可减少控制变量，但无法改善上游长期供给不足。

## 方案与边界

不改动会保留白屏、变动端口和复杂自动缓冲。原样照搬 OK影视 144 MB 内存目标会增加低内存电视风险。本轮采用固定阈值、保留 JKTV 原有设备内存上限：仅 Exo 自动档且无用户覆写时，使用单个 Media3 `DefaultLoadControl`（50 秒目标、1 秒启动、2 秒重缓冲），并让 Media3 自行选择带宽计量；关闭该档的自动网络调速、动态调度及自动画质约束。自定义或已有覆写保留原策略。原生硬解、HDR、音轨、字幕和 IJK 路径不改。此改动是简化候选，不能保证该 4K 外部代理视频不卡。

切普通站点时保留旧网页，等新站点内容布置好再显示原生首页；保留播放与站源本机服务原有的 9978–9998 备用端口，同时提供独立的局域网日志入口 9977，仅处理 `/debug/` 路径。若 9977 被占用，日志入口回退到本机服务当前端口并记录原因，不影响播放服务。更改不触及账号、配置和备份。

## 验收与回退

- GitHub Leanback ARM64 编译、固定签名、包名、版本、APK 摘要通过；本地检查未把额外文件带入提交。
- 电视用同一个站点复测白屏；用 `http://电视IP:9977/debug/logs` 下载日志；用同一影片观察首帧、缓冲次数/时长、音视频和硬解状态。端口被占用、真实网络吞吐和白屏像素结果都须真机核实。
- 回退至已安装的 1.6 APK；固定签名允许覆盖路径，但若系统不接受降版本，需保留数据备份后处理。代码回退本次提交即可恢复旧策略。
